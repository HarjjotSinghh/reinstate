# ADR 0005: v0.6.0 scope, and Windows-first acceptance while the macOS host is away

## Status

Accepted 2026-09-05 by the maintainer's instruction; the five decisions below
are the assumptions the release runs under. Each is also listed as a question
in [`docs/planning/v0.6.0-hop/clarifications.md`](../planning/v0.6.0-hop/clarifications.md)
so the maintainer can overturn it before stable promotion.

## Context

Stable is `v0.5.1` (2026-08-21). Two bodies of work are finished and
uncertified:

- `v0.5.2-rc.1` (2026-08-23, on `main`): the interactive CLI, OpenCode and
  Grok Build at T3/T4, Qwen at T4. Its 22-row acceptance contract requires a
  tagged artifact on both platforms; no device report exists (#366).
- `hop/main` (131 commits past `main`): the complete Hop client, OpenCode T5,
  Kimi T2, keyring format 5. Its hosted control plane (`hopd`, private repo)
  is built and green but deployed nowhere; `https://hop.reinstate.dev` does
  not resolve. Fifteen of eighteen hosted tickets are closed; #6 (deploy),
  #16 (Windows parity), #17 (launch) are open.

Every prior stable was promoted on fresh Apple Silicon macOS and native
Windows x64 evidence (`RELEASING.md`, preconditions). The macOS host is in
repair until roughly 2026-09-19. The maintainer has directed that releases
proceed on Windows evidence alone until it returns, and that the next stable
be `v0.6.0`.

## Decisions

**D1 — `v0.6.0` ships the Hop client ahead of the hosted service.** The
client is already registered unconditionally (hosted ADR 0007) and reverting
it would be the largest change in the release. Instead every surface says the
truth: `docs/hop.md`, the README, and the website state that the hosted
control plane is not yet open; `rein login` against a control plane it cannot
reach reports that in one sentence and points at the docs; the control-plane
URL stays configurable (`REINSTATE_HOP_URL`, `[hop] url`) so labs and
self-hosters can use the client today. No pricing, billing, or "sign up"
language ships in this release.

**D2 — Windows-first acceptance waiver.** `v0.6.0-rc.N` candidates and the
stable promotion are gated on native Windows x64 (`windows/amd64`, never WSL)
only. Every row the prior contracts require on macOS is carried as *deferred*,
listed in a public issue, and re-run against the same stable tag when the
hardware returns. No document, data file, or release note may state that
`v0.6.0` was verified on macOS. If the macOS run then fails, the fix ships as
`v0.6.1`, not by editing the record. This mirrors the `v0.2.0` reconciliation
that limited verified support to two platforms: the boundary is narrowed and
named, not hidden.

**D3 — Verified ranges widen on single-platform evidence, marked as such.**
The host runs Claude Code `2.1.261` and OpenCode `1.18.27`, outside the
`2.1.219`–`2.1.238` and `1.18.21` ranges. Downgrading the maintainer's daily
tools is not acceptable, and running acceptance with `--allow-untested` would
make every resume row vacuous. The ranges therefore widen through the
installed versions on native Windows physical resume evidence, and
`docs/compatibility.md` plus the website compatibility JSON say "Windows
evidence; macOS pending" for the widened part until the macOS run lands.

**D4 — No stable `v0.5.2`.** Its content is certified inside `v0.6.0`. #366
is re-pointed at the `v0.6.0` Windows run; the macOS half joins the D2 issue.

**D5 — `v0.6.0` is a minor, not a patch.** Bare `rein` changes behaviour on a
terminal, new top-level commands land, `config.toml` gains `[hop]`, and
keyring format 5 is a clean cutover. Pre-1.0 policy permits this in a minor
with changelog notice (`ROADMAP.md`, stable release policy). Phase 6C ships
here; Phase 6A (universal configuration) moves to `v0.7.0`.

## Consequences

- `RELEASING.md` gains a "v0.6.0 Windows-first waiver" section under the
  supported-platform boundary, and the `v0.6.0-rc.1` candidate gate cites it.
- A new contract, `docs/testing/v0.6.0-windows-acceptance.md`, composes the
  Phase 5 generated matrix (178 rows at this catalog), the 22-row CLI matrix,
  and the Hop parity journeys (hosted #16) into one Windows column with an
  explicit deferred-macOS table.
- `ROADMAP.md` Phase 6 splits: 6C "Cloud continuity (Hop)" ✅ in `v0.6.0`
  with the deferred-macOS note; 6A/6B 📋 for `v0.7.0`.
- The website's `product.ts` keeps `requiresAccount: false` (the hosted tier
  is optional and not open); `releaseStatus` names Windows-only acceptance.
- Signed tags remain a founder action: the release signing key is not on the
  Windows host and must not be copied there by an agent.
- D2 governs claims about `v0.6.0` acceptance. Device journeys recorded
  before this ADR (the August OpenCode, Grok Build, Qwen, and Hop records on
  macOS and native Windows) keep their dates and platforms wherever they are
  cited; what no surface may say is that `v0.6.0` itself was accepted on
  macOS.

## Alternatives rejected

- *Hold everything until the macOS host returns.* Two idle weeks on a
  finished tree, against the maintainer's explicit direction.
- *Cut stable `v0.5.2` first, then `v0.6.0`.* Two Windows-only stables for
  one body of evidence; the CLI rows would be run twice.
- *Strip the Hop commands behind a build tag for `v0.6.0`.* Contradicts
  hosted ADR 0007, touches every Hop file, and would be reverted at launch.
- *Keep the ranges and pin older agent builds on the host.* Downgrades the
  maintainer's working tools and tests a version nobody will run.

## Amendment 2026-09-07

`v0.6.0-rc.2`'s tagged Windows run surfaced two rows the required-row rule
in D2 (as written, `PARTIAL`/`NOT TESTED` never pass a required row) makes
permanently unpassable on this host, for reasons neither a product fix nor
operator action on this device can resolve:

- `opencode:D4` tests that a partial-final-record capsule truncates at a
  byte-exact JSONL boundary. OpenCode's shipped catalog source is
  SQLite-only; its store has no JSONL record boundary at all, so the row's
  mechanism cannot exist for this agent's store layout. This is not a
  fixture gap (like `grok:D4` was) or a product defect — it is definitional.
- `qwen:E1`/`E2`/`E3`/`E5` require a completed non-interactive Qwen Code
  turn. The acceptance host's Qwen Code OAuth token is expired; refreshing
  it requires an interactive browser login only the maintainer can perform.
  Qwen Code is listed as an optional agent in
  `docs/testing/v0.6.0-windows-acceptance.md` (`Required environment`) —
  never installed solely for a row — precisely so that one vendor's
  unavailability on a given host does not gate the release.

As written, D2's required-row rule makes a `PASS` device verdict impossible
on this host regardless of product state, which was never the intent: a
Windows-first stable should not wait indefinitely on a store layout that
cannot carry the tested mechanism, or on a browser login to a vendor the
contract itself calls optional. This ADR is therefore amended, autonomously,
to unblock the stable gate:

- **Rule (a) — definitional.** A row whose mechanism cannot exist for an
  agent's store layout, regardless of any fix, is recorded
  `N/A (definitional)` with the reason and excluded from the required row
  count. Today this is exactly `opencode:D4`. It is never silently dropped:
  every such row is named in the report, every time, so a second one is a
  new finding to evaluate, not a precedent to invoke.
- **Rule (b) — host credential, optional agents only.** A row for an agent
  the contract lists as optional that cannot complete because that agent's
  vendor credential on the host is expired or absent is recorded
  `NOT TESTED (host credential)` and does not block the device verdict,
  provided the same row is `PASS` for every required agent and for at least
  one other optional agent at the same tier, and the report names every
  such row and the credential it depends on.
- Full text of both rules, and how they combine with the pre-existing rule
  for everything else, lives in
  [`docs/testing/v0.6.0-windows-acceptance.md`](../testing/v0.6.0-windows-acceptance.md#dispositions-that-do-not-block-the-device-verdict)
  rather than being duplicated here.

Both rules exist to keep a Windows-first stable movable: a single
definitional row and a single optional agent's host credential must not gate
`v0.6.0` indefinitely, any more than the Apple Silicon macOS hardware gap
itself does under D2. Neither rule loosens what a *required* agent must do,
narrows the platform boundary D2 already drew, or lets a future row claim
this disposition without the same test: mechanism cannot exist (a), or
credential unavailable on an agent the contract already calls optional (b).

This amendment was adopted without the maintainer's prior sign-off, to
unblock a stable gate the D2 rule as written made unreachable. It is listed
as Q19 in `docs/planning/v0.6.0-hop/clarifications.md` for the maintainer to
accept or reject. Rejecting rule (b) means stable waits for the Qwen Code
login (Q18) so those four rows can complete. Rejecting rule (a) means
`opencode:D4` reverts to `NOT TESTED (definitional)`, which under the D2
rule never passes a required row, so stable then waits for the maintainer
either to drop that row from the required set explicitly or to accept the
rule after all; no code change can make it pass.

## Amendment 2 (2026-09-08)

Two things this amendment records, both settled by the maintainer's own
answer to Q27 in `docs/planning/v0.6.0-hop/clarifications.md`
(2026-09-07) plus what the `v0.6.0-rc.5` rechecks (§23, §24 of
`docs/testing/results/2026-09-07-windows-v060rc5.md`) then showed about
`MatrixH:H7`.

**Vendor self-update policy (Q27, adopted).** D3 already widens a verified
range on single-platform Windows evidence when the host's own installed
agent build has moved past the prior ceiling; Q27 asked whether the
acceptance lab should instead pin vendor CLI versions for the duration of a
run so evidence stays tied to one known version per agent. The maintainer's
standing answer, adopted: **do not pin.** When a vendor CLI self-updates
past the verified ceiling mid-cycle, widen the range on native Windows
evidence rather than block — Reinstate always wants to support the latest
version a real user is actually running, and pinning would test a version
nobody has. This is D3's rule made explicit as ongoing policy, not a new
mechanism: each widening is real evidence from a real self-update, named as
such, the same way `grok` (`1.0.5`→`1.0.13`), `qwen` (`0.21.13`→`0.23.0`), and
`opencode` (`1.18.27`→`1.18.29`) were each widened over this release's own
candidates. The companion rule for the case where a version drift is
*found mid-run*, rather than resolved by widening before the run starts, is
recorded in `docs/testing/v0.6.0-windows-acceptance.md`'s dispositions
section: the affected rows are `NOT TESTED (version drift)` for that run,
and the next candidate carries the widened range.

**`MatrixH:H7`'s live-home check, refined.** The corrected lab-isolation
rule this ADR's first amendment's sibling document change (Q25) added —
fresh Hop account, before/after digest equality of the live agent-home
roots — got its first three tagged-artifact exercises across the `v0.6.0-rc.5`
run and its two same-artifact rechecks. All three reached, or nearly
reached, the daemon mechanism; none produced a clean `PASS`. Two separate
problems surfaced, not one: `#424` itself (the Task-Scheduler-spawned
daemon follows the ambient login environment, not the environment
`daemon install` ran under, so it read live agent trees even when the
installing shell's own environment was correctly isolated) and, independent
of `#424`, that byte-for-byte digest equality of a live agent-home root is
not a measurable pass condition on a heavily-used, multi-session
development host — ordinary concurrent activity changes those roots
between any two timestamps regardless of what `rein` did. The two rechecks'
own evidence (a per-file diff attributing every changed line to a process
other than `rein`, once a full before-listing was actually preserved) shows
the mechanism can be verified without digest equality. `H7`'s live-home
check is refined accordingly — full text in
[`docs/testing/v0.6.0-windows-acceptance.md`](../testing/v0.6.0-windows-acceptance.md#run-notes)
rather than duplicated here: a full per-file before/after listing of only
the session-bearing subtrees, a `PASS` condition built on zero snapshots
restored plus per-entry attribution rather than aggregate-digest equality,
and every differing entry named in the report regardless of disposition.
The operator go-signal mechanism is unchanged.

**`#424` scheduled.** The design gap itself — pinning the agent-root
environment a daemon was installed under, so a Task-Scheduler restart
cannot silently follow a different one — is scheduled for `v0.6.1`, not
this release: it is a small, separable product fix, already understood and
already filed, and the refined live-home check above lets `H7` verify the
daemon round-trip mechanism on `v0.6.0` without waiting for it.
