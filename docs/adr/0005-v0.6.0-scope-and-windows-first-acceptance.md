# ADR 0005: v0.6.0 scope, and Windows-first acceptance while the macOS host is away

## Status

Accepted 2026-09-05 by the maintainer's instruction; the five decisions below
are the assumptions the release runs under. Each is also listed as a question
in [`docs/planning/v0.6.0-hop/clarifications.md`](../planning/v0.6.0-hop/clarifications.md)
so the maintainer can overturn it before stable promotion.

## Context

Stable is `v0.5.1` (2026-08-21). Two bodies of work are finished and
uncertified:

- `v0.5.2-rc.1` (2026-08-23, on `main`): the interactive CLI, OpenCode and
  Grok Build at T3/T4, Qwen at T4. Its 22-row acceptance contract requires a
  tagged artifact on both platforms; no device report exists (#366).
- `hop/main` (131 commits past `main`): the complete Hop client, OpenCode T5,
  Kimi T2, keyring format 5. Its hosted control plane (`hopd`, private repo)
  is built and green but deployed nowhere; `https://hop.reinstate.dev` does
  not resolve. Fifteen of eighteen hosted tickets are closed; #6 (deploy),
  #16 (Windows parity), #17 (launch) are open.

Every prior stable was promoted on fresh Apple Silicon macOS and native
Windows x64 evidence (`RELEASING.md`, preconditions). The macOS host is in
repair until roughly 2026-09-19. The maintainer has directed that releases
proceed on Windows evidence alone until it returns, and that the next stable
be `v0.6.0`.

## Decisions

**D1 — `v0.6.0` ships the Hop client ahead of the hosted service.** The
client is already registered unconditionally (hosted ADR 0007) and reverting
it would be the largest change in the release. Instead every surface says the
truth: `docs/hop.md`, the README, and the website state that the hosted
control plane is not yet open; `rein login` against a control plane it cannot
reach reports that in one sentence and points at the docs; the control-plane
URL stays configurable (`REINSTATE_HOP_URL`, `[hop] url`) so labs and
self-hosters can use the client today. No pricing, billing, or "sign up"
language ships in this release.

**D2 — Windows-first acceptance waiver.** `v0.6.0-rc.N` candidates and the
stable promotion are gated on native Windows x64 (`windows/amd64`, never WSL)
only. Every row the prior contracts require on macOS is carried as *deferred*,
listed in a public issue, and re-run against the same stable tag when the
hardware returns. No document, data file, or release note may state that
`v0.6.0` was verified on macOS. If the macOS run then fails, the fix ships as
`v0.6.1`, not by editing the record. This mirrors the `v0.2.0` reconciliation
that limited verified support to two platforms: the boundary is narrowed and
named, not hidden.

**D3 — Verified ranges widen on single-platform evidence, marked as such.**
The host runs Claude Code `2.1.261` and OpenCode `1.18.27`, outside the
`2.1.219`–`2.1.238` and `1.18.21` ranges. Downgrading the maintainer's daily
tools is not acceptable, and running acceptance with `--allow-untested` would
make every resume row vacuous. The ranges therefore widen through the
installed versions on native Windows physical resume evidence, and
`docs/compatibility.md` plus the website compatibility JSON say "Windows
evidence; macOS pending" for the widened part until the macOS run lands.

**D4 — No stable `v0.5.2`.** Its content is certified inside `v0.6.0`. #366
is re-pointed at the `v0.6.0` Windows run; the macOS half joins the D2 issue.

**D5 — `v0.6.0` is a minor, not a patch.** Bare `rein` changes behaviour on a
terminal, new top-level commands land, `config.toml` gains `[hop]`, and
keyring format 5 is a clean cutover. Pre-1.0 policy permits this in a minor
with changelog notice (`ROADMAP.md`, stable release policy). Phase 6C ships
here; Phase 6A (universal configuration) moves to `v0.7.0`.

## Consequences

- `RELEASING.md` gains a "v0.6.0 Windows-first waiver" section under the
  supported-platform boundary, and the `v0.6.0-rc.1` candidate gate cites it.
- A new contract, `docs/testing/v0.6.0-windows-acceptance.md`, composes the
  Phase 5 generated matrix (178 rows at this catalog), the 22-row CLI matrix,
  and the Hop parity journeys (hosted #16) into one Windows column with an
  explicit deferred-macOS table.
- `ROADMAP.md` Phase 6 splits: 6C "Cloud continuity (Hop)" ✅ in `v0.6.0`
  with the deferred-macOS note; 6A/6B 📋 for `v0.7.0`.
- The website's `product.ts` keeps `requiresAccount: false` (the hosted tier
  is optional and not open); `releaseStatus` names Windows-only acceptance.
- Signed tags remain a founder action: the release signing key is not on the
  Windows host and must not be copied there by an agent.
- D2 governs claims about `v0.6.0` acceptance. Device journeys recorded
  before this ADR (the August OpenCode, Grok Build, Qwen, and Hop records on
  macOS and native Windows) keep their dates and platforms wherever they are
  cited; what no surface may say is that `v0.6.0` itself was accepted on
  macOS.

## Alternatives rejected

- *Hold everything until the macOS host returns.* Two idle weeks on a
  finished tree, against the maintainer's explicit direction.
- *Cut stable `v0.5.2` first, then `v0.6.0`.* Two Windows-only stables for
  one body of evidence; the CLI rows would be run twice.
- *Strip the Hop commands behind a build tag for `v0.6.0`.* Contradicts
  hosted ADR 0007, touches every Hop file, and would be reverted at launch.
- *Keep the ranges and pin older agent builds on the host.* Downgrades the
  maintainer's working tools and tests a version nobody will run.
