# v0.6.0-rc.5 tagged-artifact acceptance prompts

Use these prompts only after the signed `v0.6.0-rc.5` GitHub prerelease is
published and both live installer routes pin that exact tag. They specialize
the release-neutral
[`v0.6.0` native Windows acceptance contract](v0.6.0-windows-acceptance.md),
which itself composes the
[Phase 5 acceptance contract](phase-5-universal-agent-coverage-acceptance.md),
the [`v0.5.2` CLI experience contract](v0.5.2-cli-experience-acceptance.md),
and hosted ticket #16 into one Windows column, under the
[Windows-first waiver](../../RELEASING.md#v060-windows-first-waiver) in
[ADR 0005](../adr/0005-v0.6.0-scope-and-windows-first-acceptance.md).

`v0.6.0-rc.5` is a corrective candidate. `v0.6.0-rc.4` was published and its
own tagged-artifact acceptance
([`docs/testing/results/2026-09-07-windows-v060rc4.md`](results/2026-09-07-windows-v060rc4.md))
ended device verdict `FAIL` — **208 PASS / 1 PARTIAL / 4 FAIL / 2 NOT
TESTED** of **215** required rows. Both of that candidate's own fixes — the
Pi reader indexing `message.content`, and the widened Qwen Code range — were
fully confirmed (every `pi`/`qwen` row `PASS`). Seven required rows blocked
the verdict; `v0.6.0-rc.5` fixes the code and contract-text findings among
them.

- **`MatrixB:B4`** (product, confirmed redaction gap). The `gemini` agent's
  probed `tree` included two real, un-normalized project-name directory
  segments under `tmp/`, verbatim from the acceptance host; every path
  segment *beneath* each was correctly shape-normalized, only the top
  segment was not. Root cause: the shape rules that split a stem into a
  fixed prefix plus a hash or trailing counter returned that prefix as the
  raw regex capture, never checked against the vendor allowlist, so a
  plain project name rode through unshaped whenever it matched one of
  those patterns' generic shape. Every captured prefix is now validated
  the same way a whole stem is.
- **`MatrixB:B7`** (product, confirmed correctness gap). An overridden
  agent root (`CLINE_DATA_DIR`) that exists but is empty was
  indistinguishable from one that does not exist at all —
  `doctor --agents --json` output was byte-identical apart from the
  timestamp in both cases. Every RootEnv- and fixture-root override now
  contributes its own `candidate_roots` entry carrying
  `exists`/`marker_present`.
- **CLI row `13`** (product, confirmed interactive-CLI defect). The
  interactive switcher's default `ScopeAll` scope showed every visible
  session as unresumable regardless of true state — the most common
  real-world launch condition. Root cause: `Probe` starts one goroutine per
  visible row, and a page with many more rows than any single project ever
  holds fanned out that many concurrent environment verifications at once,
  exhausting the shared per-report timeout budget before otherwise-healthy
  checks could finish. `internal/tui/readiness.Prober` now bounds
  concurrent verifications to a small fixed pool regardless of page size.
- **`MatrixG:G4`** (documentation/contract, not a regression). `push`/
  `pull --agent` completion already includes `opencode` alongside
  `claude`/`codex`, matching identical shipped behavior `v0.6.0-rc.3`'s own
  G4 row scored `PASS`; the contract's row text was stale. Corrected to
  read "Claude Code, Codex CLI, OpenCode at T5, and no other agent's" (see
  [`phase-5-universal-agent-coverage-acceptance.md`](phase-5-universal-agent-coverage-acceptance.md)).
- **`opencode:E5`, `opencode:E6`** (host/harness — version-compatibility
  block, not a credential gap). The acceptance host's real OpenCode
  self-updated to `1.18.29`, above the in-tree verified ceiling `1.18.27`,
  so both rows correctly refused with `exit 5` before reaching a scoreable
  outcome. Widened to `1.18.21`–`1.18.29` on native Windows evidence, under
  ADR 0005 D3. See
  [`docs/testing/results/2026-09-07-windows-range-widening-opencode-v060.md`](results/2026-09-07-windows-range-widening-opencode-v060.md).

The remaining blocking row from the `v0.6.0-rc.4` tagged run —
`MatrixH:H7` — is operator/elevation-availability, not a product or contract

## Fixed release identity and evidence boundary

- `TEST_TAG` is exactly `v0.6.0-rc.5`; `TEST_COMMIT` is its peeled literal
  40-character commit and must be an ancestor of `origin/main`. **`TEST_COMMIT`
  is filled in once the signed tag exists** — it is not yet known while this
  candidate is only a reviewed release commit on `release/v0.6.0-rc.5`.
- Require an annotated tag with a valid signature against
  `.github/allowed_signers` and a published non-draft prerelease tied to it.
- Install from the live bootstrap into a new directory after proving the
  bootstrap pins exactly `v0.6.0-rc.5`. Never replace a user binary.
- Require `rein` and `reinstate` to have identical bytes and to report that
  tag and full commit (`rein version --json`). Report both the tag and the
  full commit in the device report header.
- Rebuild the local session index. Do not replay a stale index without
  exercising the reader's own upgrade path.
- **Host environment.** Every shell that runs `rein`, the Hop lab, or a Go
  test must `unset REINSTATE_BACKEND REINSTATE_MEMORY_BACKEND_DIR` first;
  `rein` honours `REINSTATE_BACKEND` before it reads the profile, so a
  contaminated shell silently uses a local store and every Hop row reports
  nothing to the control plane. The report must state that every shell did
  this. Do **not** unset the host's `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or
  `XDG_DATA_HOME`: they are its live agent homes, and a Claude Code run
  spawned without `CLAUDE_CONFIG_DIR` falls back to a stale `~/.claude` that
  cannot refresh its sign-in. Isolate a row by pointing the vendor's home
  variable at your own directory. This rule is unchanged from `v0.6.0-rc.4`.
- No real transcripts, prompts, credentials, or private paths in the report.
  `MatrixB:B4`'s and `MatrixB:B7`'s evidence plants only synthetic
  directory/file names in a throwaway tree, never a real project name from
  the host.

## Lab isolation for `MatrixH:H7`

The `v0.6.0-rc.4` dispatch's "fresh lab account" wording for `H7` was
ambiguous and was read by that run's executor as a fresh **Windows user**
account, which needs administrator rights to create and could not be set up
this run, so the row was abandoned before its own UAC prompt was reached.
The rule, corrected (2026-09-07,
[issue #424](https://github.com/HarjjotSinghh/reinstate/issues/424); see
[`v0.6.0-windows-acceptance.md`](v0.6.0-windows-acceptance.md#run-notes)):

- **"Fresh Hop lab account"** means a new **Hop** account created through
  the lab's `hopd` (`hoplab pair init`, or the `rein account init` flow
  against the lab control plane) that has had **zero sessions pushed to
  it** — not a new Windows OS user account. Creating it needs no elevation
  beyond the row's own single UAC prompt for the daemon install/elevation
  step; it does not require a new Windows login. Because that account's
  Reinstate profile holds zero sessions, the scheduled daemon's pull step —
  even if it silently follows the login environment exactly as `#424`
  describes — is a no-op: there is nothing synthetic for it to write into a
  live store, real or otherwise.
- Before starting the round trip, record a **before** listing digest of
  each of the live `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, and `XDG_DATA_HOME`
  roots: for each root, list every file's path (relative to the root) and
  size in bytes, sort the list, and take its SHA-256. Record all three
  digests in the report.
- Run the round trip: `rein daemon install`, the elevation (UAC) prompt,
  `rein daemon status`, then `rein daemon stop`/`rein daemon start` under
  the same elevated context.
- After the round trip, take the same three listing digests again. All
  three must be **byte-for-byte identical** to their before-digests — the
  same file paths, the same sizes, in the same sorted order, hashing to the
  same value. Record all three post-digests in the report. A mismatch is a
  regression (`#424` recurring) and blocks the row regardless of whether
  the daemon's own mechanism otherwise appeared to work.
- `H7` still needs the maintainer at the keyboard for the one UAC prompt
  the elevation raises — this method does not remove that requirement and
  must not attempt to route around it (see "Harness traps" below). Start
  the wait only **after every other row in the executor's part is already
  done**, not in parallel with them: poll
  `D:/ReinstateAcceptanceProjects/h7-go.txt` every **60 seconds**, for **up
  to 150 minutes**, and do not attempt the elevation until that file exists
  and its content confirms the maintainer is present to accept the prompt.
  If the file never appears within that full wait window, record `PARTIAL`
  (operator/harness availability) with that reason — a shorter poll window
  is not a basis for `PARTIAL`.

This lab-isolation method is a harness clarification only; it does not
change `rein daemon install`'s own behavior (that is `#424`'s own fix, not
attempted by this candidate) and does not change what `MatrixH:H7`'s row
scores on.

## Reading a refusal correctly

Several refusals in this product are correct behaviour and must not be scored
as defects. A row fails only when the refusal is wrong, not when it fires.

- `working directory is a different repository than the source session` — run
  from the session's own workspace.
- `the recorded Git branch cannot be verified outside a Git repository` — the
  chosen session's workspace is not a repository; choose one that is.
- `source session is active; close it or pass --allow-active` — the operator is
  running that agent. For an embedded store, any write to the database counts.
- `native agent version X is outside the verified range` — the host's vendor CLI
  auto-updated past the ceiling. Pin the verified version or record the drift.
- `could not reach the Reinstate Hop control plane at <url>: <cause>` (H1c) —
  correct when the control plane genuinely does not resolve; the row passes on
  the message shape and the `control_plane_unreachable` `--json` kind, not on
  the control plane being reachable.

## Harness traps that produce a wrong verdict

Physical acceptance on this program has repeatedly found more harness defects
than product defects, and some have been **false passes**. Check the harness
before concluding the product is wrong.

- Read each agent's `root_env` from `rein doctor --agents --json` rather than
  assuming a variable name. Redirecting with a variable the product does not
  declare tests the operator's real root, not the copy.
- Put the candidate on `PATH` under **both** `rein` and `reinstate`, or an
  installed release answers instead and the comparison runs between two
  builds.
- A `--dry-run` capsule is a preview and carries no `raw_source` boundary.
  Only a harness that truncates a copied source can measure the fidelity rows
  that need it.
- Assert that a refusal **names a range**, not that it names a particular
  version. Hardcoded bounds stop testing the message the moment a ceiling
  moves.
- A Hop row that passes without exercising its mechanism is `FAIL`. Check the
  harness (the lab's env, the isolated home, `hopd.db`) before trusting a
  green result.
- Attribute a write before blaming it on a refresh. Any agent the operator is
  running writes to its own root continuously, and the audit may itself be
  running inside one.
- `MatrixB:B4` specifically: use a synthetic tree, never the real host's
  `~/.gemini`, and confirm the fixture actually contains an ordinary-looking
  project name before trusting a `PASS` — a fixture built only from
  already-suspicious names (hyphens, digits) would pass even against the
  unfixed normalizer.
- `MatrixB:B7` specifically: confirm the "existing but empty" directory
  genuinely exists and genuinely lacks the vendor's marker file before
  comparing it against the absent-path case — a directory that already has
  the marker is a different row's fixture, not this one's.
- CLI row `13` specifically: launch from a working directory that is
  genuinely outside every tracked project, and use a row count large enough
  to have exhausted the pre-fix timeout budget — a small lab that never
  fanned out enough concurrent checks to hit the exhausted-budget condition
  would pass even against the unfixed prober.
- `opencode:E5`/`E6` specifically: the ConPTY console must stay open and the
  vendor process genuinely active for the entire window between launching it
  and running the `rein resume` probe from the other shell — a console that
  already closed, or a process that already exited, produces a false
  `agent.active: false`/`unknown` that looks like the version block
  persisting rather than a timing mistake in the retry itself. Confirm
  `opencode --version` reports `1.18.29` (or later, recording the exact
  version) before attempting either row.
- `MatrixH:H7` specifically: "fresh Hop lab account" means a new **Hop**
  account with zero pushed sessions, not a new Windows OS user account —
  do not abandon the row over a missing Windows account elevation the rule
  does not actually require. Do not attempt an unattended elevation
  workaround (a scheduled task that self-elevates, a stored credential,
  etc.) to route around the missing operator — the row's mechanism is the
  real UAC prompt, and routing around it is a false pass. Start the
  go-signal poll only after every other row in the part is done, not
  before, and not in parallel.
