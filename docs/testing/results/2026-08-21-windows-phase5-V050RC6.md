## 12. Upgrade path

The row-level and source-level change detection in releases before this
candidate could not tell that Reinstate itself had changed, so an existing index
was never re-read and a reader fix reached nobody. This is invisible to a clean
run, so it was exercised deliberately.

An index built by the previous release, then opened by the tagged binary: 24 Gemini sessions with 0 resolved workspaces became 24 sessions with 10 resolved, with no row lost. A second run stayed warm at the same counts, and the previous release could still reopen the upgraded index. The 14 still unresolved are legacy digest-named directories from older Gemini versions whose path is recorded nowhere; SHA-256 cannot be inverted, so they are unresolvable by construction rather than by defect.

## 13. Findings and dispositions

No release-blocking findings.

B4 passes on this device but does not exercise the fix. The OpenCode object stores here hold only packed objects, so no loose object name of the affected length exists for the normalizer to collapse, and OpenCode declares no root environment variable, so the probe cannot be redirected at a root that has one. Two attempts at a targeted check on this device were vacuous before that was established. Windows evidence for the fix is therefore the internal/agents/probe unit tests, which cover the affected length and pass on windows-latest in CI. It is not this row. The end-to-end evidence is on the macOS device, whose root does contain loose objects.

A10 and H4 first failed on this device. Both were caused by physical E1/E2 journeys running concurrently with the matrix, which creates and removes sessions under the audited roots and invalidates a source fingerprint mid-measurement. Re-run in isolation with nothing else touching the host, A10 saw no file modified or removed and H4 measured a warm refresh at 0.37s against a 10.21s cold refresh, 96 percent faster. The isolated figures are the reported ones.
