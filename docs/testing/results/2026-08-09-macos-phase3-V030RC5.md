## 7. Findings and repository hygiene

### Release-blocking

1. **macOS acceptance host cannot supply the physical preconditions for the
   product-behavior matrix.** Two independent conditions each individually
   prevent every native-launch row:
   - **Agent versions outside the documented supported ranges.** Installed
     Claude Code is `2.1.225` (documented `2.1.219`–`2.1.220`) and installed
     Codex is `0.147.0` (documented `0.133.0`–`0.146.0`). The product correctly
     refuses both with `agent.version status=unknown severity=block` and exit
     `5`, launching nothing. Per the RC5 dispatch this fail-closed behavior is
     recorded and the documented ranges are **not** widened in this report PR.
   - **Throwaway agent homes have no vendor credentials.** A fresh
     `CLAUDE_CONFIG_DIR` reports not-logged-in and a fresh `CODEX_HOME` returns
     `401 Unauthorized`, so no genuine working vendor session or real
     continuation can be produced. The dispatch forbids reading or modifying the
     operator's real `~/.claude` / `~/.codex` trees, and the acceptance contract
     forbids installing or repairing vendor configuration on the operator's
     behalf, so neither condition may be remediated by the device agent.

   Consequence: rows 6, 7, 8, 22, 24, 25, 27, 28, 29 and 32 cannot pass, and
   rows 11, 14, 17–20, 23, 30, 31 were not reached. This is a host-provisioning
   blocker. **No product defect was observed on this host**; every behavior
   actually exercised was truthful and fail-closed.

   Remediation for a future run: provision the acceptance host with a Claude
   Code build inside `2.1.219`–`2.1.220` and a Codex build inside
   `0.133.0`–`0.146.0`, and authenticate the throwaway agent homes before the
   device agent starts, then re-run the complete matrix on the same
   `TEST_COMMIT`.

### Non-blocking

1. **Porcelain fuzz surface flaked under concurrent host load.** The first
   `FuzzParsePorcelainV2` smoke run exited `1` with `context deadline exceeded`
   while the race suite, a GoReleaser snapshot and the performance harness were
   competing for the same machine; the fuzzing execution rate collapsed to
   `0/sec`. The isolated re-run exited `0` with roughly 10.8M executions at
   `380k–1.96M/sec` and wrote no crash corpus. Classified as a host-contention
   flake. Complete first-run and re-run output is retained in private evidence.
   Test-harness scheduling, not the product, should be corrected: the fuzz
   smoke surfaces should not run concurrently with the race suite and snapshot.

### Test-harness deviations

1. The device agent ran the automated gates concurrently with early corpus and
   performance work to save wall-clock time. This caused the non-blocking fuzz
   flake above. All affected results were re-run in isolation before being
   recorded; no gate result in §3 rests on a contended run.
2. `REINSTATE_SKIP_PATH_UPDATE=1` was set during bootstrap installation so the
   live installer would not append a `PATH` line to the operator's shell
   profile. This mirrors the Windows column's `Process` PATH-scope requirement
   and was verified to leave the profile byte-unchanged. The installer's
   download, pin-verification, checksum and install behavior was exercised
   unmodified.
