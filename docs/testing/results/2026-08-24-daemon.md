# Daemon (`rein daemon`) — macOS launchd round trip and Windows Task Scheduler, 2026-08-24

Physical checks for ticket #10 (the resident per-device daemon): the
foreground loop pushing after a session change and pulling on a schedule,
the launchd user agent install/start/stop/uninstall round trip on macOS,
and the Task Scheduler registration on native Windows. Recorded against
`hop/10-daemon` at `63efa04e` (public client). Every command and output
below is real; the recovery code is redacted where it appeared. The lab
uses only synthetic session stores (a hand-written Claude fixture under a
lab `CLAUDE_CONFIG_DIR`); no real agent store was read.

## Verdict

- **Loop, macOS:** `PASS`. The daemon pulled and pushed the fixture at
  start-up, pushed again three seconds after three appends one second
  apart (debounced and coalesced into one push), and a scheduled pull
  found everything already synced. `rein daemon status` reported it
  running with the last push and pull; the stop wrote a stopped status.
- **launchd install round trip, macOS:** `PASS`. `install` wrote the
  plist under `~/Library/LaunchAgents`, bootstrapped it, and started it
  (`launchctl print` showed `state = running`); `stop` unloaded it,
  `start` reloaded and ran it once (`runs = 1`, then `runs = 2` on a
  second start of the already-loaded agent — restart in place, no double
  spawn), and `uninstall` booted it out and removed the plist, leaving no
  service and no `rein daemon run` process. The log was kept.
- **Task Scheduler XML accepted, Windows:** `PASS`. `svccheck` rendered
  the task XML and ran the full install → status → stop → start →
  uninstall round trip against the real `schtasks`, from an elevated
  session: `install: ok`, status `installed=true running=True`, `stop`,
  `start`, and `uninstall` removed the task. The generated 1.2 XML with a
  logon trigger and a named principal is accepted by `schtasks /Create
  /XML`.
- **Build and tests, Windows:** `PASS`. `go build ./...`, `go vet
  ./internal/daemon/... ./internal/cli`, `go test ./internal/daemon/...`
  and `go test ./internal/cli -run 'TestDaemon|TestSessionRootFor'` all
  green. The real-fsnotify watcher test (`TestNotifyWatcherSeesWritesIn
  NewDirectories`) ran on Windows (not skipped) and passed, so the
  Windows file watcher fires.
- **Not exercised physically** (bench limits below, covered at the unit
  and macOS seams instead): the daemon loop end-to-end on Windows
  (needs the OS keyring or a re-served passphrase descriptor, neither
  reachable in this bench's non-console sessions); OS-notification
  rendering on either platform (covered by the loop's notifier seam and
  the in-process CLI journey `TestDaemonJourneyHop`); the pull-before-
  resume freshness (the daemon keeps the index fresh on a schedule — see
  the design note in `docs/hop.md`).

Two bench facts that shaped the Windows leg, recorded for the next run:

- Credential Manager (the OS keyring) is unreachable from the public-key
  SSH logon (`A specified logon session does not exist`) and from a
  non-console scheduled task, so `rein account init` — which stores the
  device key in the keyring — could not complete on the bench. The daemon
  needs the root-key model (or a re-served passphrase descriptor), so the
  full loop was not run on Windows; its watcher was verified through the
  real-fsnotify unit test instead, and the loop end-to-end through the
  in-process CLI journey and the macOS run.
- `schtasks /Create /XML` is refused with `ERROR: Access is denied.` from
  an Administrator's **non-elevated** interactive token (a `/IT`
  scheduled task on this account). The same command succeeds from an
  elevated session. The fix that made the XML acceptable at all was
  naming the task principal's `UserId` (commit `63efa04e`); a standard
  (non-admin) user creates a per-user logon task without elevation, but
  an admin account under UAC needs an elevated shell to register a task
  in the root folder. The elevated round trip below proves the XML and
  the whole lifecycle.

## 2. macOS: the loop under launchd

Home and lab set up with a synthetic Claude session and the disk-backed
memory backend; `rein init` (BYO) then `rein account init` (root-key
model, recovery code re-entered through the automation descriptor — the
`accountinit` fixture). Then:

```text
$ rein daemon status   # before install
service:  launchd com.reinstate.daemon.8c892bfb, not installed
daemon:   never ran for <lab>/home
log:      <lab>/home/daemon/daemon.log

$ rein daemon install --env REINSTATE_BACKEND=memory --env REINSTATE_MEMORY_BACKEND_DIR=<lab>/locker \
    --env CLAUDE_CONFIG_DIR=<lab>/claude --env CODEX_HOME=<lab>/codex --env XDG_DATA_HOME=<lab>/xdg \
    --env REINSTATE_S3_ACCESS_KEY_ID=labkey --env REINSTATE_S3_SECRET_ACCESS_KEY=labsecret
installed launchd com.reinstate.daemon.8c892bfb (/Users/harjjotsinghh/Library/LaunchAgents/com.reinstate.daemon.8c892bfb.plist)
the daemon starts at login and is starting now; rein daemon status shows it, log: <lab>/home/daemon/daemon.log

$ rein daemon status   # 1s after install
service:  launchd com.reinstate.daemon.8c892bfb, installed (running)
daemon:   running (pid 28390) since 2026-08-23T22:27:01+05:30, fsnotify watch, byo
```

(`--env` is a hidden lab-only flag on `install`: it bakes extra
environment into the service so the daemon sees the synthetic stores and
the disk-backed backend. Production needs none of it.)

The service label carries an 8-hex suffix because the lab home is not the
default `~/.reinstate`; that is `LabelFor` giving a non-default home its
own service so two homes can each run a daemon.

launchd's own view, and the daemon's status after the start-up pull and
push:

```text
$ launchctl print gui/501/com.reinstate.daemon.8c892bfb | grep -E 'state|runs|pid ='
	state = running
	runs = 1
	pid = 28760

$ rein daemon status   # 9s after start
service:  launchd com.reinstate.daemon.8c892bfb, installed (running)
daemon:   running (pid 28760) since 2026-08-23T22:27:08+05:30, fsnotify watch, byo
push:     pushed 0 snapshot(s), skipped 1 unchanged, just now
pull:     pulled 0 snapshot(s), skipped 1 already synced, just now
```

A change to the fixture drives one coalesced push (three appends one
second apart, then quiet), from the daemon log:

```text
2026/08/23 16:52:48 daemon started pid=15506 backend=byo watch=fsnotify roots=2
2026/08/23 16:52:48 pull: pulled 0 snapshot(s), skipped 0 already synced
2026/08/23 16:52:52 push: pushed 1 snapshot(s), skipped 0 unchanged
2026/08/23 16:53:24 change: <lab>/claude/projects/…/session-daemon.jsonl
2026/08/23 16:53:25 change: <lab>/claude/projects/…/session-daemon.jsonl
2026/08/23 16:53:26 change: <lab>/claude/projects/…/session-daemon.jsonl
2026/08/23 16:53:31 push: pushed 1 snapshot(s), skipped 0 unchanged
```

Three changes at 16:53:24–26 produced a single push at 16:53:31 — the
debounce coalesced them, and the push landed ~3s after the last change,
never during the burst.

Stop, start (in place, no double spawn), and uninstall:

```text
$ rein daemon stop
stopped com.reinstate.daemon.8c892bfb
$ rein daemon status
service:  launchd com.reinstate.daemon.8c892bfb, installed (not loaded)
daemon:   stopped (last heartbeat just now)

$ rein daemon start        # already loaded → restart in place
started com.reinstate.daemon.8c892bfb
$ launchctl print … | grep runs
	runs = 2                 # one restart, not a second concurrent agent

$ rein daemon uninstall
uninstalled launchd com.reinstate.daemon.8c892bfb; the log under <lab>/home/daemon is kept
# afterwards: 0 plists, 0 rein daemon run processes, launchctl print → not found
```

The first `start`/`status` pass that spawned twice and read an endpoint's
nested `state = active` was caught here and fixed in `e3b0e6e` (start a
loaded agent with `kickstart -k`, bootstrap only an unloaded one; read
the service's own first `state =` line). The output above is the re-run
after that fix.
