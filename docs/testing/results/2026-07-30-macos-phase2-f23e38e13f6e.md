## 12. Findings

### Release-blocking

**F-1 — `rein fork codex:<id>` mis-attributes the vendor fork to the source
session, making the fork unaddressable and contaminating the source record.**

Observed, in one physical run:

1. `rein fork codex:019fb245-…` launched the correct process
   (`ps` argv `codex fork 019fb245-…`) in the recorded workspace.
2. The vendor created a new rollout file whose
   `session_meta.payload.session_id` is its **own** new id
   `019fb28c-…-ce2a69e99ca1`, with `forked_from_id = 019fb245-…`. The same file
   also replays source history records that carry the **source** id.
3. Reinstate indexed that file under the **source** identity and emitted
   `coalesced_session_segments: coalesced 2 local records for one native session`.
4. Consequences:
   - `rein resume codex:019fb28c-…` → `session not found`, exit `2`;
   - `rein inspect codex:019fb28c-…` → `session not found`, exit `2`;
   - the fork never appears in `rein sessions` as its own identity;
   - the **source** record absorbed the fork: `message_count 10 → 24`,
     `size_bytes 112951 → 254089`, and the fork's user prompt (including the
     fork-only controlled marker) is searchable under the source composite
     reference, even though the source's own rollout file is byte-for-byte
     unchanged and does not contain that marker.

This breaks four mandatory results of runbook section 11 for Codex: distinct
native identity, refresh discovering both source and fork, each resuming
through its vendor's native path, and changing the fork not changing the
source.

Root cause, `internal/sessionindex/codex.go` lines 121–128: the identity loop
iterates `[event, payload]` and, for `index == 0`, accepts `id`/`sessionId`/
`session_id` from **any** top-level record regardless of type — the
`session_meta` guard only constrains the payload map. Last write wins, so the
replayed source-id records overwrite the fork's own `session_meta` identity.
`forked_from_id` is not consulted.

Suggested fix direction (not applied — no product code was modified): take the
native identity from the first `session_meta` record only, and treat a record
carrying `forked_from_id` as establishing a **new** identity whose parent is the
source, so coalescing never merges a fork segment into its source.

Coverage gap: no automated test exercises a Codex fork rollout shape
(`session_meta.payload.session_id` = fork id, `forked_from_id` = source id,
plus replayed source-id records). `TestCoalesceRecordsMergesNativeSessionSegments
Deterministically` covers legitimate continuation segments only, which is why
this passed every merge gate. Retest scope for the fix: that new fixture, the
full `sessionindex` and `cli` suites, `make verify`, and a repeat of physical
rows 21, 22, 23, and 16 on both devices.

### Non-blocking

**N-1 — uncalled vulnerability in a required module.** `make verify`'s
`govulncheck` pass reports `GO-2026-5932` in `golang.org/x/crypto@v0.54.0`,
`Fixed in: N/A`, not reachable from Reinstate's call graph. `verify` exits `0`.
Worth tracking until an upstream fix exists.

**N-2 — warning volume on a real corpus.** The first refresh over the real
vendor trees emitted 16 warning lines, 13 of them one-per-record
`oversized_record` notices for individual Codex JSONL records above 4 MiB. The
bounded-record guard behaves correctly and the containing sessions were still
indexed, but a per-session summarised count would be friendlier than one line
per record on human output.

**N-3 — runbook wording conflicts with actual `rein list` behaviour.** Runbook
section 6 item 5 states that `rein list` "is not expected to work from this
fresh configless home". In practice `rein list` exits `0` from the fresh
configless home and prints Phase 1 adapter output (tab-separated
`agent / id / project-key`) that is clearly distinct from `rein sessions`. The
product behaviour is correct — `list` is not redefined as the Phase 2 canonical
listing — so the runbook sentence should be corrected rather than the code.

**N-4 — child exit codes are not mirrored.** A native child exiting `42`
surfaces as Reinstate exit `1`. This matches the documented stable table in
`docs/cli-reference.md` (`1 = unexpected runtime failure`) and preserves the
Phase 1 contract, so it is recorded as expected behaviour, not a defect.

### Test-harness deviations

**D-1** `timeout(1)` is not present on macOS; a small `perl` alarm wrapper was
used for bounded vendor invocations.

**D-2** An isolated `CLAUDE_CONFIG_DIR` was attempted first so the real vendor
tree would not be touched; the vendor rejected it with `Not logged in`. Auth
files were **not** copied. The run therefore used the real vendor root with all
filesystem inspection confined to the disposable project's own subdirectory.
The first controlled Claude attempt also returned vendor `API Error: 529
Overloaded` and was retried; that attempt's session
(`claude:e000c8ee-…`) is listed in section 4 because it is part of the
controlled corpus.

**D-3** `codex exec` consumed the inherited pipe as stdin and blocked; it was
re-run with stdin from `/dev/null`.

**D-4** The Codex TUI cannot be driven from a bare PTY harness: it blocks
waiting for terminal capability replies (`OSC 10/11`, `DSR`, `DA1`, kitty
keyboard) and, on this machine, was additionally blocked on an interactive
vendor **update prompt** (`Update available! 0.145.0 -> 0.146.0`). The
identical behaviour reproduced with `codex resume <id>` invoked **directly**,
with Reinstate entirely out of the loop, so it is a vendor/harness interaction
and not a Reinstate defect. Rows 21 and 23 were driven through GNU `screen`
attached from a real `Terminal.app` window, which the vendor accepts.

**D-5** Row 16's "the new session becomes the newest eligible record" was
asserted against the controlled corpus rather than globally, because the
operating agent's own live Claude Code session is inherently the newest record
on this device. Global deterministic ordering was separately verified across all
records with zero violations.

No deviation was converted into a `PASS`.
