## 7. Findings and repository hygiene

### Release-blocking

- None.

### Non-blocking

- **Verified Claude Code range trails the current vendor release.** RC1 pins
  the verified Claude Code range to `2.1.219`–`2.1.220`, matching
  `docs/compatibility.md`. Claude Code `2.1.222` is available on this device and
  is correctly refused as a non-overridable `agent.version` compatibility block
  with exit `5`. That refusal is the specified fail-closed contract and is
  recorded as passing evidence for row 15, but it means a user on a current
  Claude Code build cannot natively resume or fork with this candidate.
  Certification was therefore performed against `2.1.220`, which is inside the
  verified range. Widening the range requires its own physical evidence and is
  recommended as an input to the stable `v0.3.0` decision; it is not an RC1
  acceptance failure.
- **Gemini CLI physical path not exercised.** Gemini CLI is genuinely absent on
  this device and the runbook forbids installing it solely for acceptance, so
  its optional read-only path is `NOT TESTED`. The equivalent OpenCode path was
  exercised physically and passed.

### Test-harness deviations

- The curated performance PATH resolves Claude Code through a directory
  containing a symbolic link to the vendor's own installed `2.1.220` executable,
  so that the certified configuration uses a version inside the verified range
  while the device default remains `2.1.222`. The resolved executable is the
  vendor's own regular file, outside the source and performance evidence roots;
  no wrapper, source build, generated fixture or evidence-owned executable was
  introduced.
- Vendor logins were performed into throwaway agent home directories dedicated
  to this run. The developer's real agent configuration trees were never read or
  modified.
- An initial verifier-timeout probe appeared to take 30 s. That measurement was
  an artifact of a two-process test stub whose orphaned child kept the output
  pipes open. Re-measured with a single-process stub, the documented two-second
  verifier deadline is enforced at about 2.03 s. No product defect is implied.
- A malformed-UTF-8 *filename* fixture could not be created because APFS
  rejects such names. Malformed UTF-8 was instead injected into configuration
  content, and the renderer produced valid UTF-8 output.

### Repository hygiene

- Report-only diff: this commit adds exactly one file,
  `docs/testing/results/2026-08-05-macos-phase3-V030RC1.md`.
- Product files changed: `0`.
- Merge-base with `TEST_COMMIT`: the branch is created directly from
  `f6bdbaae83b8fc2b4ce769787c8fc1bba6c79bc6`.
- Privacy scan: no transcript, prompt, response, secret, credential, MCP
  configuration value, instruction content, skill content, dirty filename, diff
  body, raw child error, or private absolute path appears in this report.
- Supersessions: none. No row failed and was re-run; every recorded result is
  its original observation.
- This evidence is append-only. It will not be amended or force-pushed after the
  commit is shared.

### Reconciled outcome

The two required platforms disagree. Apple Silicon macOS passed all 32 required
rows with zero release-blocking findings. Native Windows x64 failed 23 of 32
required rows with six release-blocking findings. Under the RC1 dispatch,
`rc1_tagged_artifact_acceptance=PASS` requires both devices to reach 32 `PASS`
with zero required `PARTIAL`/`FAIL`/`NOT TESTED` and zero release blockers, so
**RC1 tagged-artifact acceptance is `FAIL`**.

Both devices agree on the parts of the candidate that are platform-independent.
Identity, provenance and the installer chain passed on both: matching full
commit, matching signed-artifact digests, valid attestations, and correct
installer pinning. Performance passed on both, with every logical command inside
its device ceiling, zero timeouts, validated results, alias parity, clean
workspaces and unmutated vendor fingerprints. The Windows warm p95 range of
44.583–945.422 ms is inside the Windows ceilings, and no 20–30 second regression
was observed on either device. Issue #96 therefore has passing installed-artifact
latency evidence on both supported platforms even though Windows acceptance
failed for other reasons.

The Windows failures separate into two classes, and the maintainer decision
should treat them differently.

**Host-tooling gaps, not product defects.** Windows blockers 2 and 3 record that
GoReleaser was not installed (`make snapshot` exit `2`, staging exit `1`) and
that `unzip`, `sha256sum` and `jq` were unavailable so the shell release-artifact
helper exited `127`. These are missing prerequisites on the certification host.
They are correctly recorded as release blockers because the dispatch requires
those gates to run, but they do not by themselves demonstrate a defect in the
candidate. Re-running them on a Windows host with the required toolchain is the
cheapest way to reduce the failing set.

**Candidate-affecting findings.** Windows blocker 1 records
`CGO_ENABLED=1 go test -race ./... -count=1` exiting `1` in `internal/cli`. The
same gate passed on macOS, so this is a platform-specific test or product
failure that must be diagnosed before any promotion. Windows blocker 5 records
that Windows executable trust did not resolve the installed `codex.exe`,
producing executable, layout and version blockers and compatibility exit `5` for
Codex resume and fork. Blockers 4 and 6 are consequences: without a discoverable
fresh Claude session and a resolvable Codex executable, the rows that depend on
real same-vendor sessions, real terminal warning policy, picker behaviour and
capability privacy could not produce required evidence, and missing required
evidence is `FAIL` rather than `PASS`.

One caveat on attribution, recorded so the maintainer does not over-trust a
single device's diagnosis. The Windows report attributes blocker 5 to the
resolver probing the extensionless `codex` name. The coordinator could not
reproduce that mechanism from macOS. `internal/executabletrust/resolve.go`
resolves candidates through `exec.LookPath(filepath.Join(directory, name))`, and
Go's Windows implementation of `LookPath` does apply `PATHEXT` extensions even
for a path containing separators, so the extensionless probe alone would not
obviously fail to find `codex.exe`. The observed symptom is accepted as reported;
its stated root cause should be confirmed on Windows before a fix is designed,
since the real cause may instead lie in trust-boundary filtering, the allowlisted
environment handed to the probe, or the installed Codex launcher's actual file
name and extension.

Neither report is amended by this reconciliation, both pull requests remain
draft and unmerged, and no product file is modified. Stable `v0.3.0` remains
unauthorized. That is independent of the RC1 result: RC1 acceptance is not a
stable promotion decision, and stable promotion additionally requires a separate
maintainer decision and fresh tagged-artifact validation on both supported
platforms under `RELEASING.md`.
