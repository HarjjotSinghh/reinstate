# v0.6.0-rc.4 tagged-artifact acceptance prompts

Use these prompts only after the signed `v0.6.0-rc.4` GitHub prerelease is
published and both live installer routes pin that exact tag. They specialize
the release-neutral
[`v0.6.0` native Windows acceptance contract](v0.6.0-windows-acceptance.md),
which itself composes the
[Phase 5 acceptance contract](phase-5-universal-agent-coverage-acceptance.md),
the [`v0.5.2` CLI experience contract](v0.5.2-cli-experience-acceptance.md),
and hosted ticket #16 into one Windows column, under the
[Windows-first waiver](../../RELEASING.md#v060-windows-first-waiver) in
[ADR 0005](../adr/0005-v0.6.0-scope-and-windows-first-acceptance.md).

`v0.6.0-rc.4` is a corrective candidate. `v0.6.0-rc.3` was published and its
own tagged-artifact acceptance
([`docs/testing/results/2026-09-07-windows-v060rc3.md`](results/2026-09-07-windows-v060rc3.md))
ended device verdict `FAIL` — **201 PASS / 3 PARTIAL / 1 FAIL / 10 NOT
TESTED** of **215** required rows. All 22 CLI-experience rows and all 16 Hop
parity rows passed, and that candidate's own fix — the Cursor CLI store
reader reading the real `blobs`/`meta` schema — was confirmed `PASS` on real
data (`cursor:C2`, `cursor:C3`). Fourteen required rows blocked the verdict,
of two root causes: `v0.6.0-rc.4` fixes both.

- **`pi:C3`** (product, confirmed code defect). A fresh, planted-token Pi
  session was created and completed live through Pi's own Anthropic login,
  writing a real `version:3` session with the token in a `role:"user"`
  message on disk, but `rein search` found nothing and `rein inspect` showed
  no `prompt_preview`. Root cause:
  `internal/agents/sources/pi/source.go`'s `readConversation` handed the
  whole `message` object to the shared text-flattening helper
  (`ExtractTextContent`), whose `map[string]any` branch only reads a
  top-level `"text"` key and never descends into `message.content[].text` —
  the real shape. The reader now reads `message.content` directly.
- **`qwen:D1`–`D5`, `E1`/`E2`/`E3`/`E5`/`E6`** (10 rows, host/harness —
  version-compatibility block, not a credential gap). The acceptance host's
  real Qwen Code self-updated to `0.23.0`, above the in-tree verified
  ceiling `0.21.12`–`0.21.13`, so every launch-plan-building row correctly
  refused with `exit 5` before reaching a scoreable outcome. Widened to
  `0.21.12`–`0.23.0` on native Windows physical-resume evidence, under
  ADR 0005 D3. See
  [`docs/testing/results/2026-09-07-windows-range-widening-qwen-v060.md`](results/2026-09-07-windows-range-widening-qwen-v060.md).

The other three blocking rows from the `v0.6.0-rc.3` tagged run —

## Fixed release identity and evidence boundary

- `TEST_TAG` is exactly `v0.6.0-rc.4`; `TEST_COMMIT` is its peeled literal
  40-character commit and must be an ancestor of `origin/main`. **`TEST_COMMIT`
  is filled in once the signed tag exists** — it is not yet known while this
  candidate is only a reviewed release commit on `release/v0.6.0-rc.4`.
- Require an annotated tag with a valid signature against
  `.github/allowed_signers` and a published non-draft prerelease tied to it.
- Install from the live bootstrap into a new directory after proving the
  bootstrap pins exactly `v0.6.0-rc.4`. Never replace a user binary.
- Require `rein` and `reinstate` to have identical bytes and to report that
  tag and full commit (`rein version --json`). Report both the tag and the
  full commit in the device report header.
- Rebuild the local session index. Do not replay a stale index without
  exercising the reader's own upgrade path.
- **Host environment.** Every shell that runs `rein`, the Hop lab, or a Go
  test must `unset REINSTATE_BACKEND REINSTATE_MEMORY_BACKEND_DIR` first;
  `rein` honours `REINSTATE_BACKEND` before it reads the profile, so a
  contaminated shell silently uses a local store and every Hop row reports
  nothing to the control plane. The report must state that every shell did
  this. Do **not** unset the host's `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or
  `XDG_DATA_HOME`: they are its live agent homes, and a Claude Code run
  spawned without `CLAUDE_CONFIG_DIR` falls back to a stale `~/.claude` that
  cannot refresh its sign-in. Isolate a row by pointing the vendor's home
  variable at your own directory. **This rule is exactly why `MatrixH:H7`
  needs the lab-isolation method below** — the daemon does not currently
  honour an isolated home once Task Scheduler restarts it (issue #424).
- No real transcripts, prompts, credentials, or private paths in the report.
  `pi:C3` below plants its own token in a session this run creates and may
  quote that token; nothing else may quote a real prompt, title, or
  identifier from a session this run did not create.

## Lab isolation for `MatrixH:H7`

The `v0.6.0-rc.3` tagged run's `H7` round trip wrote synthetic content into
this host's real, live `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, and
`XDG_DATA_HOME` (report §16, §21;
[issue #424](https://github.com/HarjjotSinghh/reinstate/issues/424)): the
scheduled daemon Task Scheduler starts runs with the operator's ordinary
login environment, not the isolated environment `rein daemon install` ran
under, because the task definition pins only `--home`, not the agent-root
variables. `rein` itself is unchanged this candidate — the row's mechanism
is still the real daemon and the real UAC prompt — but the run method around
it changes so a repeat incident is impossible rather than merely unlikely:

- Run `H7` from a **fresh lab account** — a Windows user account with **no**
  real or synthetic Claude, Codex, or OpenCode sessions ever pushed to it
  (a brand-new `CLAUDE_CONFIG_DIR`/`CODEX_HOME`/`XDG_DATA_HOME`, or accounts
  that genuinely have none). Because that account's Reinstate profile holds
  zero sessions, the scheduled daemon's pull step — even if it silently
  follows the login environment exactly as `#424` describes — is a no-op:
  there is nothing synthetic for it to write into a live store, real or
  otherwise.
- Before starting the round trip, record a **listing digest** of each of
  that account's live Claude, Codex, and OpenCode roots: for each root,
  list every file's path (relative to the root) and size in bytes, sort the
  list, and take its SHA-256. Record all three digests in the report.
- Run the round trip: `rein daemon install`, the elevation (UAC) prompt,
  `rein daemon status`, then `rein daemon stop`/`rein daemon start` under
  the same elevated context the prior run used.
- After the round trip, take the same three listing digests again. All
  three must be **byte-for-byte identical** to their before-digests — the
  same file paths, the same sizes, in the same sorted order, hashing to the
  same value. Record all three post-digests in the report. A mismatch is a
  regression (`#424` recurring) and blocks the row regardless of whether the
  daemon's own mechanism otherwise appeared to work.
- `H7` still needs the maintainer at the keyboard for the one UAC prompt
  the elevation raises — this method does not remove that requirement and
  must not attempt to route around it (see "Harness traps" below, carried
  from the `v0.6.0-rc.3` dispatch). Before starting `H7`, poll
  `D:/ReinstateAcceptanceProjects/h7-go.txt` for the maintainer's go-ahead:
  do not attempt the elevation until that file exists and its content
  confirms the maintainer is present to accept the prompt. If the file
  never appears within the run's time budget, record `PARTIAL` with that
  reason, exactly as `v0.6.0-rc.2`'s and `v0.6.0-rc.3`'s runs did when no
  acceptor was available.

This lab-isolation method is a harness change only; it does not change
`rein daemon install`'s own behavior (that is `#424`'s own fix, not
attempted by this candidate) and does not change what `MatrixH:H7`'s row
scores on.

## Reading a refusal correctly

Several refusals in this product are correct behaviour and must not be scored
as defects. A row fails only when the refusal is wrong, not when it fires.

- `working directory is a different repository than the source session` — run
  from the session's own workspace.
- `the recorded Git branch cannot be verified outside a Git repository` — the
  chosen session's workspace is not a repository; choose one that is.
- `source session is active; close it or pass --allow-active` — the operator is
  running that agent. For an embedded store, any write to the database counts.
- `native agent version X is outside the verified range` — the host's vendor CLI
  auto-updated past the ceiling. Pin the verified version or record the drift.
- `could not reach the Reinstate Hop control plane at <url>: <cause>` (H1c) —
  correct when the control plane genuinely does not resolve; the row passes on
  the message shape and the `control_plane_unreachable` `--json` kind, not on
  the control plane being reachable.

## Harness traps that produce a wrong verdict

Physical acceptance on this program has repeatedly found more harness defects
than product defects, and some have been **false passes**. Check the harness
before concluding the product is wrong.

- Read each agent's `root_env` from `rein doctor --agents --json` rather than
  assuming a variable name. Redirecting with a variable the product does not
  declare tests the operator's real root, not the copy.
- Put the candidate on `PATH` under **both** `rein` and `reinstate`, or an
  installed release answers instead and the comparison runs between two
  builds.
- A `--dry-run` capsule is a preview and carries no `raw_source` boundary.
  Only a harness that truncates a copied source can measure the fidelity rows
  that need it.
- Assert that a refusal **names a range**, not that it names a particular
  version. Hardcoded bounds stop testing the message the moment a ceiling
  moves.
- A Hop row that passes without exercising its mechanism is `FAIL`. Check the
  harness (the lab's env, the isolated home, `hopd.db`) before trusting a
  green result.
- Attribute a write before blaming it on a refresh. Any agent the operator is
  running writes to its own root continuously, and the audit may itself be
  running inside one.
- `pi:C3` specifically: plant a token that exists nowhere else, and confirm
  the session file's own bytes on disk carry `message.content` parts before
  trusting `rein`'s own read of it — a fixture frozen to the legacy
  `version:1` shape would pass even against the unfixed reader.
- Every `qwen` row specifically: confirm `rein inspect qwen:<id> --json`
  reports `agent.version.status=match` (not `unknown`/`untested`) before
  attempting the row's own mechanism — a row run against the wrong Qwen
  Code binary, or before the widened ceiling actually took effect in the
  built binary, produces a false `exit 5` that looks like an unfixed
  candidate rather than a harness mistake.
- `codex:E5`/`opencode:E5`/`grok:E5` specifically: the ConPTY console must
  stay open and the vendor process genuinely active for the entire window
  between launching it and running the `rein resume --dry-run` probe from
  the other shell — a console that already closed, or a process that
  already exited, produces a false `agent.active: false`/`unknown` that
  looks like the harness gap persisting rather than a timing mistake in the
  retry itself.
- `MatrixH:H7` specifically: do not attempt an unattended elevation
  workaround (a scheduled task that self-elevates, a stored credential,
  etc.) to route around the missing operator — the row's mechanism is the
  real UAC prompt, and routing around it is a false pass. Do not skip the
  fresh-lab-account requirement above to save setup time — reusing an
  account with real agent data is exactly what turned the `v0.6.0-rc.3`
  attempt into a real host-data incident.
