# v0.6.0-rc.1 tagged-artifact acceptance prompts

Use these prompts only after the signed `v0.6.0-rc.1` GitHub prerelease is
published and both live installer routes pin that exact tag. They specialize
the release-neutral
[`v0.6.0` native Windows acceptance contract](v0.6.0-windows-acceptance.md),
which itself composes the
[Phase 5 acceptance contract](phase-5-universal-agent-coverage-acceptance.md),
the [`v0.5.2` CLI experience contract](v0.5.2-cli-experience-acceptance.md),
and hosted ticket #16 into one Windows column, under the
[Windows-first waiver](../../RELEASING.md#v060-windows-first-waiver) in
[ADR 0005](../adr/0005-v0.6.0-scope-and-windows-first-acceptance.md).

`v0.6.0-rc.1` is the first `v0.6.0` candidate. It carries the Hop client —
sign-in, the locker, device pairing and revocation, key rotation, machine
migration, and `rein daemon` — and everything `v0.5.2-rc.1` introduced: the
interactive session switcher, the environment-warning checklist, the handoff
studio, the `rein init` wizard, and the `ctrl+k` palette. OpenCode reaches T5
(encrypted sync) and Kimi Code CLI reaches T2 (handoff source).

Publication means ready for physical acceptance; it does not mean acceptance
passed. Current stable remains `v0.5.1`. This candidate does not authorize
stable `v0.6.0`.

One mandatory device run starts this candidate's tagged-artifact acceptance:
native Windows x64 (`windows/amd64`, never WSL). Apple Silicon macOS
acceptance is **deferred** under ADR 0005 (see the "Deferred" section below)
— nothing in this candidate's evidence claims macOS.

The device must report all required rows: **178** generated by
`rein doctor --agents --acceptance-matrix --json` on the tagged binary
(section B), **22** interactive CLI rows (section C), and **16** Hop parity
journey rows (section D) — 216 required rows in total. Record each count in
the report header. A report whose Phase 5 count disagrees with the candidate
catalog is invalid. `PARTIAL` and `NOT TESTED` do not pass a required row.

## Fixed release identity and evidence boundary

- `TEST_TAG` is exactly `v0.6.0-rc.1`; `TEST_COMMIT` is its peeled literal
  40-character commit and must be an ancestor of `origin/main`. **`TEST_COMMIT`
  is filled in once the signed tag exists** — it is not yet known while this
  candidate is only a reviewed release commit on `release/v0.6.0-rc.1`.
- Require an annotated tag with a valid signature against
  `.github/allowed_signers` and a published non-draft prerelease tied to it.
- Install from the live bootstrap into a new directory after proving the
  bootstrap pins exactly `v0.6.0-rc.1`. Never replace a user binary.
- Require `rein` and `reinstate` to have identical bytes and to report that
  tag and full commit (`rein version --json`). Report both the tag and the
  full commit in the device report header.
- Rebuild the local session index. Do not replay a stale index without
  exercising the reader's own upgrade path.
- **Host environment contamination.** Every shell that runs `rein`, the Hop
  lab, or a Go test must `unset REINSTATE_BACKEND REINSTATE_MEMORY_BACKEND_DIR
  XDG_DATA_HOME` first; `rein` honours `REINSTATE_BACKEND` before it reads the
  profile, so a contaminated shell silently uses a local store and every Hop
  row reports nothing to the control plane. The report must state that every
  shell did this.
- No real transcripts, prompts, credentials, or private paths in the report.

## What this candidate specifically re-tests

**The widened Claude Code and OpenCode ranges, on this exact tagged binary.**
`v0.6.0-rc.1` widens the fail-closed Claude Code range through `2.1.261` (was
`2.1.219`–`2.1.238` at `v0.5.1`) and the OpenCode range through `1.18.27` (was
the single build `1.18.21`), both on native Windows physical resume evidence
recorded pre-tag
(`docs/testing/results/2026-09-06-windows-range-widening-v060.md`). Confirm on
the tagged binary that a session created with each ceiling version is indexed
and resumed through the launch plan Reinstate produces, returning a token that
exists only in that session's own history — and that `2.1.262` (Claude Code)
and `1.18.28` (OpenCode) still fail closed as `UNTESTED` with the refusal
naming the range, not a hardcoded version.

**The Hop journeys, H1 through H12, against the local lab.** Run every row of
section D against a disposable `hopd` plus `scripts/testing/fakelocker`
(`scripts/testing/hoplab`), never the hosted control plane (it is not
deployed) and never the developer's real agent trees. This is the first time
these rows run against a tagged artifact rather than a working tree.

**CLI rows 2 and 22, byte-identical to `v0.5.1`.** Row 2 (`rein` on a non-TTY
exits `2` with the `rein sessions --json` hint) and row 22 (every `--json`
document) are the frozen-output guard: install a `v0.5.1` binary from its
GitHub release alongside the tagged `v0.6.0-rc.1` binary and diff their output
byte-for-byte for both rows. A difference in either is a release-blocking
finding regardless of how the rest of the interactive surface behaves.

**The host contamination rule**, above — every prior tagged run on this host
found Hop rows silently reporting nothing because of a leaked
`REINSTATE_BACKEND=memory`. Confirm it is unset in the shell that runs each
row, not only in the report's preamble.

## Reading a refusal correctly

Several refusals in this product are correct behaviour and must not be scored
as defects. A row fails only when the refusal is wrong, not when it fires.

- `working directory is a different repository than the source session` — run
  from the session's own workspace.
- `the recorded Git branch cannot be verified outside a Git repository` — the
  chosen session's workspace is not a repository; choose one that is.
- `source session is active; close it or pass --allow-active` — the operator is
  running that agent. For an embedded store, any write to the database counts.
- `native agent version X is outside the verified range` — the host's vendor CLI
  auto-updated past the ceiling. Pin the verified version or record the drift.
- `could not reach the Reinstate Hop control plane at <url>: <cause>` (H1c) —
  correct when the control plane genuinely does not resolve; the row passes on
  the message shape and the `control_plane_unreachable` `--json` kind, not on
  the control plane being reachable.

## Harness traps that produce a wrong verdict

Physical acceptance on this program has repeatedly found more harness defects
than product defects, and some have been **false passes**. Check the harness
before concluding the product is wrong.

- Read each agent's `root_env` from `rein doctor --agents --json` rather than
  assuming a variable name. Redirecting with a variable the product does not
  declare tests the operator's real root, not the copy.
- Put the candidate on `PATH` under **both** `rein` and `reinstate`, or an
  installed release answers instead and the comparison runs between two
  builds.
- A `--dry-run` capsule is a preview and carries no `raw_source` boundary.
  Only a harness that truncates a copied source can measure the fidelity rows
  that need it.
- Assert that a refusal **names a range**, not that it names a particular
  version. Hardcoded bounds stop testing the message the moment a ceiling
  moves.
- A Hop row that passes without exercising its mechanism is `FAIL`. Check the
  harness (the lab's env, the isolated home, `hopd.db`) before trusting a
  green result.
- Attribute a write before blaming it on a refresh. Any agent the operator is
  running writes to its own root continuously, and the audit may itself be
  running inside one.

## Reports

- `docs/testing/results/<DATE>-windows-v060rc1-pretag.md` (pre-tag snapshot
  build; evidence that the candidate is ready for tagged-artifact acceptance,
  authorizes nothing past that)
- `docs/testing/results/<DATE>-windows-v060rc1.md` (tagged artifact; this is
  the run that can authorize stable `v0.6.0`)
- `docs/testing/results/<DATE>-windows-hop-parity-v060.md` (section D; may be
  shared by the pre-tag and tagged runs if re-run against the tagged binary
  and both identities are recorded)

Each report is committed on its own branch. `PARTIAL` and `NOT TESTED` do not
pass a required row; a missing required result is `FAIL`. Cumulative and
append-only: a `FAIL` that later passes keeps both entries and says what
changed.

Stable `v0.6.0` is authorized only when the tagged Windows report is `PASS`
with zero release-blocking findings, section E is recorded exactly as
`DEFERRED` (never as passed), and the stable promotion decision in
`RELEASING.md` names the deferred-macOS issue.
