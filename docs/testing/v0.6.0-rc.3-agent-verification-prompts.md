# v0.6.0-rc.3 tagged-artifact acceptance prompts

Use these prompts only after the signed `v0.6.0-rc.3` GitHub prerelease is
published and both live installer routes pin that exact tag. They specialize
the release-neutral
[`v0.6.0` native Windows acceptance contract](v0.6.0-windows-acceptance.md),
which itself composes the
[Phase 5 acceptance contract](phase-5-universal-agent-coverage-acceptance.md),
the [`v0.5.2` CLI experience contract](v0.5.2-cli-experience-acceptance.md),
and hosted ticket #16 into one Windows column, under the
[Windows-first waiver](../../RELEASING.md#v060-windows-first-waiver) in
[ADR 0005](../adr/0005-v0.6.0-scope-and-windows-first-acceptance.md).

`v0.6.0-rc.3` is a corrective candidate. `v0.6.0-rc.2` was published and its
own tagged-artifact acceptance
([`docs/testing/results/2026-09-07-windows-v060rc2.md`](results/2026-09-07-windows-v060rc2.md))
ended device verdict `FAIL` — **203 PASS / 5 PARTIAL / 2 FAIL / 5 NOT
TESTED** of **215** required rows. All 22 CLI-experience rows passed and 15
of 16 Hop parity rows passed; the seven required-row failures `v0.6.0-rc.1`
found were cleared. Eleven required rows blocked the verdict; of those,
`v0.6.0-rc.3` fixes exactly one root cause — the Cursor CLI store reader read
a schema (`messages`/`message`/`bubbles`) no real Cursor CLI store has,
found by that same run's own post-commit coordinator finding (report §0.12).
`cursor:C2` and `cursor:C3` were re-scored `FAIL` on that finding after the
report's own tagged evidence was assembled. This candidate changes exactly
the Cursor CLI store reader (`blobs`/`meta`, the real schema) and nothing
else: no agent tier moves, no compatibility range widens, and nothing in
Hop, the daemon, the interactive CLI, or any other agent's reader is
touched. The other nine blocking rows from the `v0.6.0-rc.2` tagged run —
`cline:C3`, `pi:C3`, `grok:E1`/`E2`/`E3`, `qwen:E1`/`E2`/`E3`,
`MatrixH:H7` — are host/harness/operator-availability gaps unrelated to the
Cursor store schema; this dispatch re-tests them under refined methods (see
"Dispositions carried" below) but they are not this candidate's fix.

Publication means ready for physical acceptance; it does not mean acceptance
passed. Current stable remains `v0.5.1`. This candidate does not authorize
stable `v0.6.0`.

## Fixed release identity and evidence boundary

- `TEST_TAG` is exactly `v0.6.0-rc.3`; `TEST_COMMIT` is its peeled literal
  40-character commit and must be an ancestor of `origin/main`. **`TEST_COMMIT`
  is filled in once the signed tag exists** — it is not yet known while this
  candidate is only a reviewed release commit on `release/v0.6.0-rc.3`.
- Require an annotated tag with a valid signature against
  `.github/allowed_signers` and a published non-draft prerelease tied to it.
- Install from the live bootstrap into a new directory after proving the
  bootstrap pins exactly `v0.6.0-rc.3`. Never replace a user binary.
- Require `rein` and `reinstate` to have identical bytes and to report that
  tag and full commit (`rein version --json`). Report both the tag and the
  full commit in the device report header.
- Rebuild the local session index. Do not replay a stale index without
  exercising the reader's own upgrade path.
- **Host environment.** Every shell that runs `rein`, the Hop lab, or a Go
  test must `unset REINSTATE_BACKEND REINSTATE_MEMORY_BACKEND_DIR` first;
  `rein` honours `REINSTATE_BACKEND` before it reads the profile, so a
  contaminated shell silently uses a local store and every Hop row reports
  nothing to the control plane. The report must state that every shell did
  this. Do **not** unset the host's `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or
  `XDG_DATA_HOME`: they are its live agent homes, and a Claude Code run
  spawned without `CLAUDE_CONFIG_DIR` falls back to a stale `~/.claude` that
  cannot refresh its sign-in. Isolate a row by pointing the vendor's home
  variable at your own directory.
- No real transcripts, prompts, credentials, or private paths in the report,
  **except** the two Cursor CLI real-store rows below, which are read-only,
  counts-and-field-names-only, under the same T1-discovery exception the
  contract already grants `C1`–`C4`.

## What this candidate specifically re-tests

**The Cursor CLI store-schema defect the `v0.6.0-rc.2` tagged run's own
post-commit finding surfaced (report §0.12).**

- **`cursor:C2`, `cursor:C3`** — confirm `message_count` and `search_text`
  now read the host's **real** Cursor CLI `store.db` schema
  (`blobs(id, data)` / `meta(key, value)`), not the
  `messages`/`message`/`bubbles` shape the `v0.6.0-rc.2` reader guessed at
  and no real store ever had. Because `cursor-agent` `2026.08.11` is broken
  on this host (`Error: Cannot find module 'tree-sitter'`, no `node_modules`
  in its installed-versions directory) and no fresh real Cursor CLI session
  can be created, these two rows run **`rein`-only, read-only, against the
  host's real root**, under the same T1-discovery exception the acceptance
  contract already grants rows `C1`–`C4`: record counts and field names
  only, never a title, prompt, path, or identifier from a session the run
  did not create. Confirm `rein sessions --agent cursor --json` reports a
  non-zero `message_count` for at least one real session, then read that
  session's own bounded `prompt_preview` yourself, choose one distinctive
  word from it, and run `rein search <word> --agent cursor --json`
  (**never quote a real prompt, title, or identifier in the report — the
  search word itself, chosen by you from your own reading, is the only
  thing that may appear**) and confirm the session is found. Also run
  `go test ./internal/agents/sources/cursor/... -count=1` against the
  committed synthetic `blobs`/`meta` fixtures for the schema-mechanism
  proof this row's dispatch history otherwise required.

**Everything else `v0.6.0-rc.2`'s tagged run left blocking is unrelated to
the Cursor store schema and is re-tested here under refined methods, not
fixed by this candidate:**

## Reading a refusal correctly

Several refusals in this product are correct behaviour and must not be scored
as defects. A row fails only when the refusal is wrong, not when it fires.

- `working directory is a different repository than the source session` — run
  from the session's own workspace.
- `the recorded Git branch cannot be verified outside a Git repository` — the
  chosen session's workspace is not a repository; choose one that is.
- `source session is active; close it or pass --allow-active` — the operator is
  running that agent. For an embedded store, any write to the database counts.
- `native agent version X is outside the verified range` — the host's vendor CLI
  auto-updated past the ceiling. Pin the verified version or record the drift.
- `could not reach the Reinstate Hop control plane at <url>: <cause>` (H1c) —
  correct when the control plane genuinely does not resolve; the row passes on
  the message shape and the `control_plane_unreachable` `--json` kind, not on
  the control plane being reachable.

## Harness traps that produce a wrong verdict

Physical acceptance on this program has repeatedly found more harness defects
than product defects, and some have been **false passes**. Check the harness
before concluding the product is wrong.

- Read each agent's `root_env` from `rein doctor --agents --json` rather than
  assuming a variable name. Redirecting with a variable the product does not
  declare tests the operator's real root, not the copy.
- Put the candidate on `PATH` under **both** `rein` and `reinstate`, or an
  installed release answers instead and the comparison runs between two
  builds.
- A `--dry-run` capsule is a preview and carries no `raw_source` boundary.
  Only a harness that truncates a copied source can measure the fidelity rows
  that need it.
- Assert that a refusal **names a range**, not that it names a particular
  version. Hardcoded bounds stop testing the message the moment a ceiling
  moves.
- A Hop row that passes without exercising its mechanism is `FAIL`. Check the
  harness (the lab's env, the isolated home, `hopd.db`) before trusting a
  green result.
- Attribute a write before blaming it on a refresh. Any agent the operator is
  running writes to its own root continuously, and the audit may itself be
  running inside one.
- `cursor:C2`/`cursor:C3` specifically: this is a read-only, `rein`-only
  reading of the host's **real** `~/.cursor` store, under the T1-discovery
  exception — do not attempt to launch `cursor-agent` (broken on this host,
  `Error: Cannot find module 'tree-sitter'`) to create a fresh session, and
  do not substitute a synthetic fixture for this row's real-data evidence —
  a synthetic fixture is what let `v0.6.0-rc.2`'s dispatch-prescribed method
  miss the real schema gap in the first place (report §0.12, §16).
- `grok:E1`/`E2`/`E3` specifically: isolate `GROK_HOME` to a directory
  seeded with nothing but `auth.json`, not the acceptance host's default
  agent home — the `v0.6.0-rc.2` stall was caused by that host's shared,
  global MCP server set repeating connect/disconnect noise on every
  `--resume` turn, and reusing the same home reproduces the same stall
  regardless of the retry method.
- `MatrixH:H7` specifically: do not attempt an unattended elevation
  workaround (a scheduled task that self-elevates, a stored credential,
  etc.) to route around the missing operator — the row's mechanism is the
  real UAC prompt, and routing around it is a false pass.
